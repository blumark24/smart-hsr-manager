# SMART HSR — Trusted Document Lifecycle Design (isolated prototype)

**Status: DESIGN/CONTRACT ONLY — NOT CONNECTED TO LIVE API OR STORAGE.**

**Parent:** [DRAFT PR #104](https://github.com/blumark24/smart-hsr-manager/pull/104) on SHA `37b4fa71384592f491a85722a617aff2d13c46b7`; original [RC #103](https://github.com/blumark24/smart-hsr-manager/pull/103) is frozen at `900ad89bf45ac29a6f4a240df7b64c1685415cc4`. This branch introduces a **pure, side-effect-free** ESM policy module and node test; it does not import the policy in any runtime application or change Firebase/Vercel/Production.

## Grounded existing defects

- Client `lands/client/lands-client.js:177–183` writes `documents` metadata with `setDoc`, *then* uploads bytes. Storage failure can create an orphaned metadata record. Client-side arbitrary `deleteDoc` compensation is **NOT** an accepted remedy.
- Same-origin embedded runtime `api/_lib/embeddedLandsRuntime.js:99–100` creates its mutation executor with `documentStorage:null`, while the `document.replace` executor requires storage and fails `DOCUMENT_STORAGE_UNAVAILABLE`. Do not bypass this guard.
- The current embedded `document.replace` runs a Storage side effect **inside a Firestore transaction callback** (`embedded-lands/server/lands-mutation-executor.js:247–263`). Firestore transactions can retry a callback, while Cloud Storage cannot participate atomically; this is a consistency/replay hazard, even once a storage adapter exists. A production design must keep external side effects **outside** retriable Firestore transactions.
- Document count and 5-axis data completeness do not prove the existence of evidence bytes or formal land-grant approval.

## Proposed server-authoritative protocol — subject to independent approval

1. **Server-authenticated INIT**: Verify Firebase ID token with the isolated Staging project, resolved municipality, active Lands membership, approved role and actual linked grant's tenant/creator. Generate non-user-controlled document ID, upload-request idempotency key and expected revision. In a Firestore transaction, assert request-id uniqueness and create `pending` document metadata. Freeze file size (1..10MiB), exact supported MIME and expected SHA-256 digest of bytes. Do NOT accept client-selected Storage object paths, approval/status fields, actor UID or tenant.
2. **Server-owned upload allocation**: Return a short-lived, least-privilege, single-object upload capability scoped to a server-derived object key and attempt number, only after the tenant and record checks. Do not pass Firebase Admin credentials to the browser. If using signed URLs, document allowed HTTP verb/content type/size/generation constraints, TTL, CORS and replay resistance. Multipart/base64 through a generic Vercel serverless route is **not** recommended because of payload, memory and cost limits. Decide provider/bucket from verified deployed Staging metadata and residency requirements, not guesses.
3. **BYTE VERIFICATION**: A trusted server inspects the exact object generation after upload, verifies size, approved MIME, and independently hashes the stored bytes. It must not trust a client-supplied `proof` or hash as confirmation. Reject mismatches and orphaned metadata. Only after valid proof, transactionally compare `revision` and `status=pending`, then mark `ready` with the verified generation and append an approved, typed, minimally identifying audit event.
4. **FAIL / RECOVER**: Mark failed with a **closed, sanitized reason set**. Retry by incrementing `attempt`, `revision` and using a different object key to avoid stale callbacks/overwrites. Limit attempts. Idempotency is enforced by Firestore uniqueness/compare-and-set, not solely by this pure reducer. A server sweeper/reconciliation job lists stale `pending` and objectively absent/mismatched objects, records failures and cleans up only server-owned keys with version-aware retention and legal-hold policies. Never blindly delete documents from the client.
5. **REPLACE**: Never overwrite the active object in a Firestore transaction. Stage a **new immutable version object** and verify it; switch the document's active version/Storage-generation atomically together with a trusted audit entry after verification. On failure preserve prior ready bytes. Old versions follow retention/legal-hold rules; cross-tenant versions are forbidden. A document delete similarly needs a staged tombstone, audit, scoped cleanup and retryable reconciliation.
6. **READ / UI**: Only `ready` with a checked version may be offered for download. Show pending/failed as such, not as uploaded evidence. Five-axis data completeness and formal grant approval remain separate dimensions. No full identity numbers in log/test evidence or UI by default. Limit disclosures by verified role/tenant.
7. **QA / GOVERNANCE**: Test unauthorized/disabled role, wrong tenant, missing parent grant, upload interrupted, wrong SHA/MIME/size, stale attempt, duplicate request/replay, concurrent callbacks, Storage succeeds but Firestore finalize fails, pending timeout and sweeper reentrancy, permission denial, retry cap, legal-hold/retention, restore rollback, and redacted audit. Obtain written security and municipal data-controller approval, PDPL/privacy impact and NCA applicability assessment, documented provider/bucket residency, then use **synthetic isolated Staging only**.

## Scope/limitations of the pure policy module

`embedded-lands/server/document-lifecycle-policy.js` defines `pending → ready/failed`, `failed → pending` retry, exact tenant/role/creator check, server-derived attempt path, SHA-256/size/MIME proof equality, bounded attempts and optimistic revision conflict. The module does **not** verify the cryptographic trust of its inputs: **only a trusted server adapter may supply server-validated identity and independently checked Storage proofs**. It does **not** contact Firestore/Storage or write audit logs and does **not** secure an actual upload by itself. Specifically, it does not solve the current two-phase upload defect or missing Storage adapter.
