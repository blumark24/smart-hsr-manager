## 2. شروط سابقة ضرورية (Preconditions)

- [ ] حساب `blumark24` هو **OWNER** لفريق Vercel؛ إنشاء مشروع منفصل عبر الموصل أعاد 403، ما يرجح نقص صلاحية التكامل وليس دور الحساب. يُنشئ المالك المشروع فارغًا من لوحة Vercel أو يراجع إعدادات صلاحيات التكامل. **ممنوع** استعارة مشروع البلدية كحل بديل. راجع كذلك شروط Vercel Hobby للاستخدام التجاري قبل التشغيل البلدي.
- [ ] مسؤول أمن المعلومات/مالك البيانات يثبتان أن بيئة Preview لا تستخدم أي Firebase Project أو Auth tenant أو Firestore أو Storage bucket حقيقي للبلدية.
- [ ] مراجعة هوية حساب الخدمة وLeast Privilege والامتيازات والسجلات والمنطقة السحابية والاحتفاظ دون وضع أسماء/قيم الأسرار في GitHub أو الدردشة العامة.
- [ ] ضبط متغيرات المشروع المنفصل باستخدام **بيانات تجريبية مُنشأة حديثًا**. لا نسخ لأسرار Production.
- [ ] اختبار Fail-closed: عند نقص إعداد أو صلاحية يجب فشل تسجيل الدخول/نقل المستخدم/رفع الملف بأمان، لا اللجوء إلى البيئة الحقيقية.
- [ ] تطبيق حماية وصول Preview (Deployment Protection) وعدم إزالة الحماية لتسهيل الاختبار.

**إذا تعذر بند:** STOP ولا تنشر، ولا تفعّل `LANDS_EMBEDDED_RUNTIME` أو تغيّر Firebase IAM/Rules.

## 3. إجراءات اختبار إصدار معزول بعد تحقق الشروط

1. تثبيت مرشح دمج **واحد** بإذن المراجع، وتسجيل SHA النهائي وكل PR وسبب دمجه. **هذا الدليل لا يسمح بالدمج نفسه**.
2. تشغيل الاختبارات المحلية ضمن Node 22 بلا أسرار Production، وFirestore Emulator منفصل. سجّل Pass/Fail على SHA نفسه.
3. نشر **Preview فقط** على مشروع اختبار منفصل من خلال حساب يملك إذن النشر؛ تأكد من `READY` + exact SHA + target `preview` + عدم وجود Alias للدومين البلدي.
4. Smoke Test قراءة فقط لمسار `/api/lands-health` ومسار التشخيص `/api/organization/context?previewGate=lands-sso`: تأكد من `ready:true` للشروط المنشورة دون تسجيل أسرار. **لا تخلط هذا مع نجاح حساب حقيقي**.
5. UAT يدوي **ببيانات اصطناعية وحسابات مخوّلة** يتضمن الدخول والخروج والمهام وتغير الدور وتبديل الخدمة وعزل التبويبات؛ U1–U8 إن كانت حسابات Staging فعلًا، ولا تفترض أنها مسجلة أو جاهزة.
6. دور الأراضي: افحص صاحب الصلاحية وغير المخوّل، ربط أمر → قرار → منحة → مستند، صلاحية الرؤية، فشل الرفع، اكتمال تخزين bytes الفعلي، الربط المحاسبي والتدقيق، ورفض إظهار هوية مستفيد خارج التفويض.
7. الحصر: بلاغ اصطناعي + موقع غير حقيقي موصوف بأنه اختبار + صورة تجريبية + تحليل Vision AI إذا كان معتمدًا في Staging + تعديل بشري + الإسناد → المعالجة → المراجعة → الإغلاق.
8. الحركة: طلب/موافقة/تسليم/عودة لمركبة افتراضية وتحقق حالات المنع، مع إثبات عدم امتداد الصلاحية لخدمات أخرى.
9. مقارنة بصرية على Desktop/820px iPad/390px Mobile، نهاري/ليلي: الهوية، القائمة اليمنى، الهيدر والاسم والدور، عدم قص النوافذ، المساعد وتحذيراته، ودقة الخريطة.
10. سجل اختبارات API/Emulator/المتصفح في ملف Evidence Matrix مع اسم المسؤول ووقت الاختبار وSHA. لا تُغلَق P0 بمجرد نجاح شكل الواجهة.

## 4. خطة النشر الآمن للإنتاج — **ليست إذن تنفيذ**

لا يُنظر في Production حتى يوقع صاحب الصلاحية والجهة المالكة للبيانات ومراجع الأمن والمنتج على:

- [ ] نتيجة Live UAT على **Preview المعزول** دون P0/P1 مفتوح.
- [ ] مطابقة الأدوار/قواعد Firestore/API وإعدادات الاتصال والبيانات للجهة المستهدفة وفق ضوابطها.
- [ ] توثيق مصدر البيانات والاستضافة وDPIA/العقود/الضوابط النظامية الواجبة بعد مراجعة المختص.
- [ ] نسخ احتياطي مستقل قابل للاستعادة والتحقق من استعادة **تجريبية** لا تستخدم سجلات حقيقية في هذه المرحلة.
- [ ] خطة Rollback بمرجع Deployment/SHA معروف، ومالك قرار وتوقيت ووسيلة إشعار وتدقيق، مع ضمان عدم إسقاط أي بيانات.
- [ ] إذن نشر **محدد النطاق والوقت** منفصل عن هذه الوثيقة، يتضمن طريقة الرصد ومعايير التراجع.

**منع مطلق:** لا ترقية تلقائية من Draft PR، لا تعديل لحسابات أو بيانات المواطنين، لا نقل ملفات أو بيانات حقيقية لبيئة العرض، ولا اعتماد الامتثال بقرار المساعد الذكي.
